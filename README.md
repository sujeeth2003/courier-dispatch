# Courier Dispatch

A small backend service that matches delivery orders to couriers in real time.
Built as a portfolio project to demonstrate clean architecture, concurrency-safe
assignment, and a measurable comparison between two matching strategies.

## What it does

- Accepts orders (`POST /orders`) with pickup/dropoff coordinates.
- Tracks live courier locations in Redis using a geospatial index
  (`POST /couriers/{id}/location`).
- Matches each new order to a courier automatically, using one of two interchangeable
  strategies (see below).
- Guarantees a courier is never double-assigned, even under concurrent load, via
  Postgres row-level locking (`SELECT ... FOR UPDATE SKIP LOCKED`).
- Exposes Prometheus metrics at `/metrics`.

## Architecture

```
                 ┌─────────────┐
  client ──POST──▶  FastAPI    │
                 │  routers    │
                 └──────┬──────┘
                        │
          ┌─────────────┼──────────────┐
          ▼                            ▼
   ┌─────────────┐             ┌───────────────┐
   │  Postgres    │◀──assign──▶│ assignment_    │
   │  (orders,    │  FOR UPDATE│ service.py     │
   │  couriers,   │  SKIP      └───────┬────────┘
   │  assignments)│  LOCKED            │
   └─────────────┘                     ▼
                                ┌───────────────┐
                                │    Redis       │
                                │  GEOADD/       │
                                │  GEOSEARCH     │
                                │  (live courier │
                                │   positions)   │
                                └───────────────┘
```

- `app/matching/` holds pure, dependency-free matching logic (haversine distance,
  nearest-courier, batch/Hungarian assignment) — unit tested without a DB.
- `app/assignment_service.py` wires that logic to Postgres + Redis, with row locking
  so concurrent requests can't grab the same courier twice.
- `app/routers/` are thin FastAPI route handlers.

## Matching strategies

- **v1 — nearest (`app/matching/nearest.py`)**: on every order creation, immediately
  finds the closest available courier by haversine distance and assigns it. Simple,
  low latency, greedy.
- **v2 — batch (`app/matching/batch.py`)**: collects orders over a time window and
  solves the assignment as an optimal bipartite matching problem using the Hungarian
  algorithm (`scipy.optimize.linear_sum_assignment`), minimizing *total* pickup
  distance across the batch rather than each order's local optimum. Falls back to a
  greedy assignment if scipy isn't installed.

The live API uses v1 by default (assignment happens synchronously on order creation,
which is what a demo of real-time dispatch should show). `app/matching/compare.py` is
a standalone script that runs both strategies over the same synthetic dataset and
reports average pickup distance, so the trade-off is directly measurable.

## Running locally

```bash
cp .env.example .env
docker compose up -d
```

This starts Postgres, Redis, and the API (`http://localhost:8000`). The API creates
its own tables on startup (`app/db.py::create_all`); `migrations/db_init.sql` is
provided as an equivalent plain-SQL script if you prefer to run migrations by hand.

Try it:

```bash
curl -X POST localhost:8000/couriers -d '' -G --data-urlencode "name=Alice"
curl -X POST localhost:8000/couriers/<id>/location -H 'content-type: application/json' \
  -d '{"lat": 37.7749, "lon": -122.4194}'
curl -X POST localhost:8000/orders -H 'content-type: application/json' \
  -d '{"pickup_lat": 37.775, "pickup_lon": -122.419, "dropoff_lat": 37.78, "dropoff_lon": -122.42}'
```

## Tests

```bash
pip install -r requirements.txt
pytest
```

- `test_matching_nearest.py` / `test_matching_batch.py` — pure unit tests, no infra
  required (haversine correctness, nearest selection, batch optimality vs. greedy).
- `test_orders_api.py` / `test_concurrency.py` — integration tests against a real
  Postgres + Redis; they auto-skip if the DB isn't reachable, and run fully in CI
  (`.github/workflows/ci.yml` starts both as services). The concurrency test fires 20
  simultaneous `POST /orders` requests at a pool of 5 couriers and asserts zero
  courier appears twice among the assignments.

## Results: v1 vs v2 matcher comparison

Generated by `python -m app.matching.compare` (50 synthetic orders, 60 couriers,
random uniform positions over a ~10km x 10km area, seed=42):

| Strategy | Assigned | Avg pickup distance (km) | Total pickup distance (km) |
|---|---|---|---|
| v1 — nearest (greedy) | 50 | 1.226 | 61.32 |
| v2 — batch (Hungarian) | 50 | 1.097 | 54.87 |

The batch/Hungarian strategy reduces average pickup distance by roughly **10.5%**
over greedy nearest-assignment on this synthetic dataset, at the cost of the 2-second
batching delay before orders are assigned. Re-run `compare.py` with different
`n_orders`/`n_couriers`/`seed` values to see how the gap changes with density.

## Notes / scope

- No authentication — out of scope for this demo.
- Order lifecycle is intentionally minimal (`pending -> assigned -> picked_up ->
  delivered`, plus `cancelled`) — just enough for matching to be meaningful.
- Schema is created via SQLAlchemy `create_all()` on startup rather than Alembic, to
  keep the project's moving parts small.
